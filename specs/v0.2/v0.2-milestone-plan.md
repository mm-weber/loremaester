| - | Host OS | Linux (so `:ro`, `chattr +i`, and CoW snapshots are all first-class) |

**Why hardened-bind over volume-clone:** on Linux, a `:ro` bind mount is kernel-enforced, so the ~34G of
static PDFs simply cannot be deleted by anything in the container and never needs frequent snapshotting.
The only frequently-changing data is vault markdown (kilobytes of diffs). Volume-clone would not have
solved the 34G question (that data is handled separately either way) while costing host IDE access and
native bind speed.

### SEC-1: Git credential hardening

**Context.** `SSH_AUTH_SOCK` is bind-mounted (`.devcontainer/devcontainer.json:76,83`) and `origin` is
SSH, so a compromised agent can use your full host SSH identity. `SecurityReview.md` records this as an
accepted residual risk.

**Requirements (EARS).**
- THE devcontainer SHALL NOT mount the host SSH-agent socket (`SSH_AUTH_SOCK`).
- THE repository SHALL default `origin` to HTTPS authenticated by a Loremaester-only fine-grained PAT
  (Contents: read/write; no Administration, no Delete), supplied via a git credential helper.
- WHERE an SSH remote is required, THE repository SHALL document a per-repo ed25519 deploy key
  (optionally loaded with `ssh-add -c`) as the fallback; the personal SSH agent is never forwarded.
- WHERE registry authentication is needed (npm, PyPI), THE setup SHALL use separate scoped tokens,
  never the git PAT.

**Acceptance.**
- [ ] No `SSH_AUTH_SOCK` mount or env in `devcontainer.json`.
- [ ] `git push` / `pull` succeed over HTTPS using the fine-grained PAT.
- [ ] Deploy-key fallback documented in the devcontainer/security docs.
- [ ] `SecurityReview.md` residual-risk entry updated.

**Refs.** List 1 #1,2,5,6,7. Pairs with SEC-2 (same file). Verified by SEC-3.

### SEC-2: Hardened bind mount

**Context.** The host repo tree is bind-mounted read-write (`workspaceMount`, `devcontainer.json:87`);
only the repo and the SSH socket are mounted (`:59-76`), no `$HOME`/parent. On Linux, read-only mounts
plus a narrow writable surface remove most of the blast radius while keeping host IDE access and native
speed. Chosen over a container-volume clone after review (see Context above).

**Requirements (EARS).**
- THE ~34G sourcebook PDFs SHALL be mounted read-only, and MAY additionally be made immutable on the
  host with `chattr +i` (the container lacks `CAP_LINUX_IMMUTABLE` to clear it).
- THE writable bind mounts SHALL be limited to the Obsidian vault and the code tree; THE devcontainer
  SHALL NOT mount `$HOME`, parent directories, or the SSH socket (removed by SEC-1).
- WHERE bundled reference material is present (skills, fixtures, static config), THE devcontainer SHALL
  mount it read-only.
- THE container SHALL be documented as disposable, with the protected remote and host-side snapshots
  (SEC-4) as the source of truth.

**Acceptance.**
- [ ] PDFs mounted `:ro`; an in-container delete attempt fails (verified).
- [ ] Only vault + code are writable; no `$HOME`/parent/socket mounts.
- [ ] VSCode "Reopen in Container" gives a working edit session.
- [ ] `SecurityReview.md` updated to the hardened-bind posture.

**Refs.** List 2 #1,2,3,7. Pairs with SEC-1 (same PR) and SEC-4 (recovery half).

### SEC-3: Remote backstops

**Context.** Token scope decides *whether* the agent can push; branch protection decides whether it can
*rewrite or destroy* history. A write-scoped token can still force-push an unprotected branch, so both
are required. `gh` is not authenticated in the container, so this is applied manually (Appendix A).

**Requirements (EARS).**
- THE `main` branch SHALL require a pull request to merge, SHALL block force-push, and SHALL block deletion.
- THE fine-grained PAT from SEC-1 SHALL NOT be able to delete the repository or modify protection rules
  (guaranteed by omitting Administration; verify).
- Repository deletion SHALL require an administrator the token does not have.

**Acceptance.**
- [ ] `main` protected: PR required, force-push blocked, deletion blocked.
- [ ] Verified: the PAT cannot delete the repo or edit protection.

**Refs.** List 1 #3,4. Closes the loop with SEC-1.

### SEC-4: Host-side recoverability

**Context.** Under the hardened bind mount, the Obsidian vault is the mutable, precious set. Its
local-only commits live in the writable mount, so an `rm -rf` destroys them; recovery must therefore be
off-container. PDFs are static and immutable; the R2R corpus (Postgres/MinIO named volumes) is derived
from the PDFs and rebuildable.

**Requirements (EARS).**
- THE vault SHALL have a host-side recovery point taken at least hourly using an incremental mechanism
  (a CoW snapshot on btrfs/ZFS/LVM, or `restic`/`borg` on ext4); full tarballs SHALL NOT be used.
- Snapshot and backup destinations SHALL NOT be mounted into the container.
- THE sourcebook PDFs SHALL be `:ro`/immutable and backed up once, on change.
- THE R2R corpus SHALL be treated as rebuildable: the repo SHALL document the rebuild path, and MAY take
  a periodic `pg_dump` if re-ingest is expensive.
- THE snapshot retention SHALL be bounded (for example hourly x24, daily x14).

**Acceptance.**
- [ ] Off-container, incremental, hourly vault snapshot in place.
- [ ] PDF immutability + one-time backup documented.
- [ ] Corpus rebuild path documented (and/or `pg_dump` scheduled).
- [ ] Retention policy configured.

**Refs.** List 2 #4. Pairs with SEC-2. Related: the R2R API is unauthenticated (`SecurityReview.md`
residual); optional API-key follow-up.

### SEC-5: Scope destructive MCP verbs + HITL

**Context.** `r2r-wrapper` exposes an ungated `delete_document`
(`mcp-servers/r2r-wrapper/r2r_mcp_wrapper.py`), and `vault-graph` exposes an ungated
`vault_rebuild_graph` (`mcp-servers/vault-graph/server.py`) that overwrites `.graph.json`. `workflow.md`
already defines manual approval gates for devcontainer/security changes.

**Requirements (EARS).**
- THE MCP servers SHALL NOT expose delete or bulk-destroy tools by default; WHERE a destructive verb is
  genuinely required, THE server SHALL require a confirmation token.
- THE harness SHALL gate irreversible shell operations (`rm -rf`, `git clean -fdx`, force-push),
  especially on the vault and `.git`, behind human approval via Claude Code hooks.
- THE harness SHALL NOT gate routine file writes (to avoid oversight-overload / rubber-stamping).

**Acceptance.**
- [ ] `delete_document` and `vault_rebuild_graph` are removed or confirmation-gated.
- [ ] Hooks require approval for `rm -rf` / `git clean -fdx` / force-push.
- [ ] Routine writes are unaffected.

**Refs.** List 2 #5,6. Coordinate with BL-1/BL-2 (same MCP files).

## Appendix B: Sourcebooks MCP server design review (detail)

The detailed backing for **BL-2** (issue #1 + structural A) and **BL-1** (issues #2-7 + structural B, C).
Deep review of `mcp-servers/sourcebooks/server.py` (126 lines, 3 tools) against the generic
`mcp-servers/r2r-wrapper/r2r_mcp_wrapper.py` (244 lines, 5 tools) and `vault-graph/server.py`
(214 lines, 5 tools).

### Architecture observations

The sourcebooks server is a **domain facade** over the generic R2R wrapper. Both call the same
`client.retrieval.search()` endpoint. The design question is whether the facade earns its keep or is a
thin layer that duplicates the wrapper without adding enough value.

| Aspect | Generic wrapper (`search`) | Sourcebooks (`search_lore`) |
|--------|---------------------------|----------------------------|
| Search mode | Caller chooses (`search_mode` param) | Hardcoded hybrid search |
| Filters | Caller builds filter dict | Domain params: `book=`, `content_type=` |
| Output format | Generic: title, type, score | Domain-aware: book_title, chapter, page_range |
| Tool surface | 5 tools (CRUD + search) | 3 tools (read-only search) |

**Verdict: the facade is justified.** Claude would otherwise need to know the filter syntax
(`{"book_title": {"$eq": "..."}}`) and remember to enable hybrid search every time. The sourcebooks
server encodes this knowledge once.

### Issues found

**1. CRITICAL: client created per call, never reused** (-> BL-2)

```python
def _get_client() -> R2RClient:
    base_url = os.environ.get("R2R_API_BASE", "http://localhost:7272")
    return R2RClient(base_url)
```

Every tool call creates a new `R2RClient`. This pattern appears in all three servers
(`r2r_mcp_wrapper.py:12`, `sourcebooks/server.py:12`; `vault-graph` does not use R2R). If `R2RClient`
opens a TCP connection or does an auth handshake, this adds latency per call. Creating per-call is safe
(no stale connections, no thread-safety concerns) but wasteful; the MCP server is a single-threaded
stdio process, so a module-level client would be fine. Decision point: cache the client instance, or is
per-call simplicity worth the overhead? Confirm whether `R2RClient.__init__` does network I/O first.

**2. IMPORTANT: `list_books` has a hard limit of 100** (-> BL-1)

```python
result = client.documents.list(limit=100)
```

If you ingest more than 100 documents (chapters), `list_books` silently truncates, with no pagination
and no warning. TTRPG sourcebooks with 20-30 chapters each mean 4-5 books hit this ceiling. Fix options:
paginate internally (loop until exhausted); expose `limit` as a tool parameter; at minimum warn when
results are truncated.

**3. IMPORTANT: `get_chapter` uses search, not retrieval** (-> BL-1)

```python
result = client.retrieval.search(query=f"{book} {chapter}", search_settings=settings)
```

`get_chapter` is semantically "give me this specific chapter" but is implemented as a search query with
book+chapter as the query string, so results are ranked by relevance not page order, the 50-chunk limit
may miss parts of long chapters, and the query biases toward chunks that mention the book/chapter names.
A more precise approach: `client.documents.list_chunks()` with a filter on `book_title` and `chapter`,
returning chunks in natural order for deterministic, complete content. Trade-off: R2R's `list_chunks`
may not support metadata filtering directly; the search approach works but is lossy for long chapters.

**4. MODERATE: no empty-result message in `search_lore`** (-> BL-1)

If `chunks` is empty, `search_lore` returns just the header `## Search Results for: query` with no
indication that nothing was found. Compare `get_chapter` ("No content found for...") and `list_books`
("No books found.").

**5. MODERATE: inconsistent attribute access patterns** (-> BL-1)

The generic wrapper uses defensive `getattr` (`getattr(chunk, "score", 0.0)`), while the sourcebooks
server accesses attributes directly (`chunk.score`). Both call the same R2R API: if one needs defensive
access, both do; if neither does (guaranteed schema), the `getattr` in the wrapper is noise.

**6. MINOR: `search_lore` is async but uses a sync `R2RClient`** (-> BL-1)

All three tools are `async def` but call `client.retrieval.search()` synchronously. R2R provides
`R2RAsyncClient`. In an MCP stdio server processing one request at a time this does not matter, but it
is a mismatched pattern.

**7. MINOR: tool docstrings are minimal** (-> BL-1)

`"""Search worldbuilding lore across source books."""` does not tell Claude that `book` should match a
`book_title` from `list_books`, or that `content_type` accepts values like `lore`, `rules`, `bestiary`.
Richer descriptions (structural item C below) help Claude select and call the tools correctly.

### Comparison with the vault-graph server

The vault-graph server is notably more robust and is a useful template: input validation
(`depth = max(1, min(depth, 4))`), error-state handling (`_check_graph()` returns specific messages for
missing/malformed data), graceful empty states ("No connections found", etc.), and a reload capability
(`vault_reload_graph`). The sourcebooks server lacks the equivalent: no input validation, partial
empty-state handling, no R2R health check.

### Structural improvements

**A. Shared client management** (-> BL-2). All R2R-based servers duplicate `_get_client()`. A shared
`r2r_utils.py` could provide a cached client:

```python
# r2r_utils.py
_client = None
def get_client():
    global _client
    if _client is None:
        _client = R2RClient(os.environ.get("R2R_API_BASE", "http://localhost:7272"))
```

## Appendix C: OCR and licensing follow-ups (R-1 to R-5)

R-1 and R-2 were completed during v0.1 release prep and are retained here as the rationale/record
(referenced by `THIRD_PARTY_NOTICES.md` for the kreuzberg removal). R-3, R-4, R-5 are the open v0.2
backlog carried by BL-3, BL-4, BL-5.

### R-1: remove the kreuzberg dependency (DONE, v0.1)

Implemented during v0.1 release prep via Conductor track `remove-kreuzberg_20260606`. OCR now lives in
`scripts/ocr_extract.py` (pypdfium2 render, then per-page tesseract/easyocr, TDD-built); `ingest_books.py`
and `extract_text.py` no longer import kreuzberg; deps, docs, and `THIRD_PARTY_NOTICES.md` are updated to
the fully-permissive stack. Rationale retained below.

`kreuzberg` powered the client-side OCR path in `scripts/ingest_books.py` and `scripts/extract_text.py`
(image-only PDFs routed through `kreuzberg.extract_file_sync`; default backend tesseract, with
EasyOCR/PaddleOCR as opt-ins). v0.1 release-prep testing found kreuzberg's OCR layer functionally
unreliable for the path it exists to serve, on top of its non-permissive license. Two independent OCR
breakages were observed inside the supported version range (evidence in R-1E):

1. **EasyOCR-on-PDF broken in kreuzberg 4.5-4.8.x.** The EasyOCR backend declared it could process a PDF
   directly (`supports_document_processing() == True`) but relied on an undeclared `pdf2image`/`pymupdf`
   dependency, so every image-only PDF failed (`ParsingError: All OCR pipeline backends failed`, or
   silently empty). Fixed only in 4.9.3.
2. **EasyOCR still broken for multi-page PDFs in kreuzberg 4.9.9 (latest stable).** A single-page PDF
   OCRs correctly, but any multi-page document returns empty text (verified at 8 and 16 pages) with no
   error raised. tesseract through the same kreuzberg path is unaffected, and standalone EasyOCR reads
   the very same rendered pages correctly, so the fault is in kreuzberg's multi-page EasyOCR execution,
   not EasyOCR, torch, CUDA, the GPU, or the documents.

License: kreuzberg (>= 4.6) is Elastic License 2.0, source-available and not OSI open-source (see
[`THIRD_PARTY_NOTICES.md`](../../THIRD_PARTY_NOTICES.md)). Removing it returns the OCR stack to a fully
permissive (MIT/Apache) footprint. The replacement is a direct pipeline: render image-only PDF pages with
a permissively-licensed renderer (`pypdfium2`, Apache/BSD; `pdf2image`+poppler also works; avoid the
AGPL-3.0 `pymupdf` in the shipped path), then OCR per page with tesseract (default, permissive) and
optionally EasyOCR (CUDA), concatenating per-page text. Per-page OCR also sidesteps the kreuzberg
multi-page bug by construction.

#### R-1E: evidence, kreuzberg EasyOCR investigation (v0.1 release prep, 2026-06)

Environment: kreuzberg 4.9.9, torch 2.9.1+cu126, easyocr 1.7.2, Python 3.12, NVIDIA GTX 1060 (compute
capability 6.1 / `sm_61`, 6 GB), Linux. Subject:
`examples/ttrpg/sourcebooks/Grunvyr-Vol-III-ImageOnly.pdf`, 16 pages, each a single full-page RGB raster
(~200 dpi, FlateDecode, no exotic codec), 15 normal dark-on-light pages + 1 dark/inverted cover.

| Layer | Test | Result |
|---|---|---|
| torch / CUDA | fp32 matmul; `get_arch_list()` vs device cc | fine (`sm_60` covers `sm_61`, CUDA minor forward-compat) |
| EasyOCR engine | `readtext` on synthetic and real rendered pages, GPU + CPU | reads them (cover p0 = 23 boxes, interior p3 = 93 boxes) |
| kreuzberg version | `==4.7.0` vs `>=4.9.3` | 4.7.0 -> "All OCR pipeline backends failed"; 4.9.3 PDF fix present but... |
| document content | dark/inverted cover | not the cause; cover-only via kreuzberg = 236 chars; inverting does not help |
| page count | single- vs multi-page via kreuzberg+EasyOCR | single-page works (p0 = 236, p3 = 1302 chars); 8 pp = 0; 16 pp = 0 |
| tesseract | same multi-page doc via kreuzberg | works (ingests all 16 pages) |

Conclusion: kreuzberg+EasyOCR returns empty for multi-page PDFs while succeeding on single pages, a
clean non-erroring failure isolated to kreuzberg's multi-page OCR path. With the earlier 4.5-4.8
regression and the Elastic-2.0 license, kreuzberg is a net liability for this project's OCR needs.
Minimal upstream repro (4.9.9): `extract_file_sync(<1-page image PDF>,
ExtractionConfig(ocr=OcrConfig(backend="easyocr")))` returns text; the identical call on an 8- or
16-page image PDF returns empty. File against `kreuzberg-dev/kreuzberg`.

### R-4: migrate Python dependency declarations to `pyproject.toml` `[project]` (OPEN v0.2 -> BL-4)

**Context.** `requirements.txt` + `requirements-dev.txt` landed as the short-term single-source-of-truth
fix for Python deps that had drifted across Dockerfile, CI, README, quickstart, and troubleshooting.
PEP 621's `[project]` table is the more modern home and aligns with the broader packaging ecosystem.

**Requirements (EARS).**
- THE project SHALL declare runtime dependencies in `pyproject.toml`'s `[project].dependencies` table.
- THE project SHALL declare test dependencies in `[project.optional-dependencies].test` (or a PEP 735
  `[dependency-groups]`).
- THE project SHALL declare a minimal `[build-system]` (likely `hatchling`) so that `pip install -e .`
  and `pip install -e ".[test]"` install the dependencies without requiring a packaged module layout.
- THE `.devcontainer/Dockerfile` SHALL install via `pip install -e ".[test]"` rather than `-r requirements*.txt`.
- THE `.github/workflows/tests.yml` SHALL install via `pip install -e ".[test]"`.
- THE `requirements.txt` and `requirements-dev.txt` files SHALL be removed once the migration lands.
- THE PEP 723 scripts under `scripts/` SHALL retain their inline metadata (they run via `uv run --no-project`).

**Effort.** Modest: the dep lists map directly onto pyproject sections. The Dockerfile change requires
verifying `pip install -e .` works against a `hatchling` config that declares no source packages
(metadata-only install, since the code lives in three separate `mcp-servers/*/server.py` files without a
packaged layout). **Out of scope:** migrating script-level PEP 723 inline deps into pyproject.

### R-5: supply-chain auto-updates, Dependabot (OPEN v0.2 -> BL-5)

**Context.** v0.1 pins every container image by `sha256` digest (compose stacks and the devcontainer
base) and the GitHub Actions by tag, but ships without an automated updater, so the pins are reproducible
yet frozen until re-pinned by hand. A ready-to-use `dependabot.yml` is staged at `specs/v0.2/dependabot.yml`,
deliberately outside `.github/`: GitHub validates `.github/dependabot.yml` on every push and rejects a
config with no active `version:` key, so a commented-out file cannot sit there.

**Requirements (EARS).**
- THE repository SHALL ship an active `.github/dependabot.yml` covering the `docker` ecosystem
  (`/.devcontainer` for the Dockerfile, `/docker` for `compose.yaml`) and `github-actions` (`/`).
- THE config SHALL group updates per ecosystem on a weekly schedule to limit PR noise.
- Dependabot version updates SHALL be enabled in repo Settings -> Code security, and the config SHALL
  live on the default branch (Dependabot reads it only there).

**Effort.** Low: `git mv specs/v0.2/dependabot.yml .github/dependabot.yml`, enable in Settings, have it on
the default branch. **Caveats:** Dependabot's `docker` ecosystem auto-detects the Dockerfile and the
standard-named `docker/compose.yaml` only; `compose.full.yaml` / `compose.app.yaml` / `compose.infra.yaml`
will NOT be auto-tracked (re-pin those manually via `docker buildx imagetools inspect <ref>` or a small
`docker/pin-images.sh`). Add a `pip` ecosystem to track the Python manifest too (`requirements*.txt`, or
the `pyproject.toml [project]` from R-4 once it lands).
