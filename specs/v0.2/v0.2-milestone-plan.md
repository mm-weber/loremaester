> milestone and its issues, folding the agent blast-radius **security hardening** together with
> the existing v0.2 backlog. Last updated: 2026-07-10. Status: **design approved, ready to create issues.**

## Context

Two inputs drive this plan:

1. The existing **v0.2 backlog** in `specs_v0.2.md`: the sourcebooks MCP design review (issues 1-7),
   R-3 collections, R-4 `pyproject` migration, R-5 Dependabot.
2. A **security remediation** analysis (two lists: SSH/git credential blast-radius, and bind-mount
   confused-deputy blast-radius) that is *new* scope but is **not unanchored**: `.devcontainer/SecurityReview.md`
   already records SSH-agent forwarding and the unauthenticated R2R API as accepted residual risks with
   exactly these suggested mitigations. The security issues below execute those flagged mitigations.

`gh` is not authenticated in the dev environment, so the milestone and issues are created **manually**.
This document is the source of truth; Appendix A holds ready-to-paste `gh` commands.

## Decisions locked

| # | Decision | Outcome |
|---|---|---|
| Q1 | Milestone scope | Security hardening **and** existing backlog, both under one `v0.2` milestone |
| Q2 | Git credentials | Document both: HTTPS+PAT primary, deploy-key fallback |
| Q3 | Repo in container | **Hardened bind mount** (reversed from an initial volume-clone pick) |
| - | 34G composition | Mostly static sourcebook PDFs; the frequently-changing data is Obsidian vault markdown |
| - | Host OS | Linux (so `:ro`, `chattr +i`, and CoW snapshots are all first-class) |

**Why hardened-bind over volume-clone:** on Linux, a `:ro` bind mount is kernel-enforced, so the ~34G of
static PDFs simply cannot be deleted by anything in the container and never needs frequent snapshotting.
The only frequently-changing data is vault markdown (kilobytes of diffs). Volume-clone would not have
solved the 34G question (that data is handled separately either way) while costing host IDE access and
native bind speed.

### SEC-1: Git credential hardening

**Context.** `SSH_AUTH_SOCK` is bind-mounted (`.devcontainer/devcontainer.json:76,83`) and `origin` is
SSH, so a compromised agent can use your full host SSH identity. `SecurityReview.md` records this as an
accepted residual risk.

**Requirements (EARS).**
- THE devcontainer SHALL NOT mount the host SSH-agent socket (`SSH_AUTH_SOCK`).
- THE repository SHALL default `origin` to HTTPS authenticated by a Loremaester-only fine-grained PAT
  (Contents: read/write; no Administration, no Delete), supplied via a git credential helper.
- WHERE an SSH remote is required, THE repository SHALL document a per-repo ed25519 deploy key
  (optionally loaded with `ssh-add -c`) as the fallback; the personal SSH agent is never forwarded.
- WHERE registry authentication is needed (npm, PyPI), THE setup SHALL use separate scoped tokens,
  never the git PAT.

**Acceptance.**
- [ ] No `SSH_AUTH_SOCK` mount or env in `devcontainer.json`.
- [ ] `git push` / `pull` succeed over HTTPS using the fine-grained PAT.
- [ ] Deploy-key fallback documented in the devcontainer/security docs.
- [ ] `SecurityReview.md` residual-risk entry updated.

**Refs.** List 1 #1,2,5,6,7. Pairs with SEC-2 (same file). Verified by SEC-3.

### SEC-2: Hardened bind mount

**Context.** The host repo tree is bind-mounted read-write (`workspaceMount`, `devcontainer.json:87`);
only the repo and the SSH socket are mounted (`:59-76`), no `$HOME`/parent. On Linux, read-only mounts
plus a narrow writable surface remove most of the blast radius while keeping host IDE access and native
speed. Chosen over a container-volume clone after review (see Context above).

**Requirements (EARS).**
- THE ~34G sourcebook PDFs SHALL be mounted read-only, and MAY additionally be made immutable on the
  host with `chattr +i` (the container lacks `CAP_LINUX_IMMUTABLE` to clear it).
- THE writable bind mounts SHALL be limited to the Obsidian vault and the code tree; THE devcontainer
  SHALL NOT mount `$HOME`, parent directories, or the SSH socket (removed by SEC-1).
- WHERE bundled reference material is present (skills, fixtures, static config), THE devcontainer SHALL
  mount it read-only.
- THE container SHALL be documented as disposable, with the protected remote and host-side snapshots
  (SEC-4) as the source of truth.

**Acceptance.**
- [ ] PDFs mounted `:ro`; an in-container delete attempt fails (verified).
- [ ] Only vault + code are writable; no `$HOME`/parent/socket mounts.
- [ ] VSCode "Reopen in Container" gives a working edit session.
- [ ] `SecurityReview.md` updated to the hardened-bind posture.

**Refs.** List 2 #1,2,3,7. Pairs with SEC-1 (same PR) and SEC-4 (recovery half).

### SEC-3: Remote backstops

**Context.** Token scope decides *whether* the agent can push; branch protection decides whether it can
*rewrite or destroy* history. A write-scoped token can still force-push an unprotected branch, so both
are required. `gh` is not authenticated in the container, so this is applied manually (Appendix A).

**Requirements (EARS).**
- THE `main` branch SHALL require a pull request to merge, SHALL block force-push, and SHALL block deletion.
- THE fine-grained PAT from SEC-1 SHALL NOT be able to delete the repository or modify protection rules
  (guaranteed by omitting Administration; verify).
- Repository deletion SHALL require an administrator the token does not have.

**Acceptance.**
- [ ] `main` protected: PR required, force-push blocked, deletion blocked.
- [ ] Verified: the PAT cannot delete the repo or edit protection.

**Refs.** List 1 #3,4. Closes the loop with SEC-1.

### SEC-4: Host-side recoverability

**Context.** Under the hardened bind mount, the Obsidian vault is the mutable, precious set. Its
local-only commits live in the writable mount, so an `rm -rf` destroys them; recovery must therefore be
off-container. PDFs are static and immutable; the R2R corpus (Postgres/MinIO named volumes) is derived
from the PDFs and rebuildable.

**Requirements (EARS).**
- THE vault SHALL have a host-side recovery point taken at least hourly using an incremental mechanism
  (a CoW snapshot on btrfs/ZFS/LVM, or `restic`/`borg` on ext4); full tarballs SHALL NOT be used.
- Snapshot and backup destinations SHALL NOT be mounted into the container.
- THE sourcebook PDFs SHALL be `:ro`/immutable and backed up once, on change.
- THE R2R corpus SHALL be treated as rebuildable: the repo SHALL document the rebuild path, and MAY take
  a periodic `pg_dump` if re-ingest is expensive.
- THE snapshot retention SHALL be bounded (for example hourly x24, daily x14).

**Acceptance.**
- [ ] Off-container, incremental, hourly vault snapshot in place.
- [ ] PDF immutability + one-time backup documented.
- [ ] Corpus rebuild path documented (and/or `pg_dump` scheduled).
- [ ] Retention policy configured.

**Refs.** List 2 #4. Pairs with SEC-2. Related: the R2R API is unauthenticated (`SecurityReview.md`
residual); optional API-key follow-up.

### SEC-5: Scope destructive MCP verbs + HITL

**Context.** `r2r-wrapper` exposes an ungated `delete_document`
(`mcp-servers/r2r-wrapper/r2r_mcp_wrapper.py`), and `vault-graph` exposes an ungated
`vault_rebuild_graph` (`mcp-servers/vault-graph/server.py`) that overwrites `.graph.json`. `workflow.md`
already defines manual approval gates for devcontainer/security changes.

**Requirements (EARS).**
- THE MCP servers SHALL NOT expose delete or bulk-destroy tools by default; WHERE a destructive verb is
  genuinely required, THE server SHALL require a confirmation token.
- THE harness SHALL gate irreversible shell operations (`rm -rf`, `git clean -fdx`, force-push),
  especially on the vault and `.git`, behind human approval via Claude Code hooks.
- THE harness SHALL NOT gate routine file writes (to avoid oversight-overload / rubber-stamping).

**Acceptance.**
- [ ] `delete_document` and `vault_rebuild_graph` are removed or confirmation-gated.
- [ ] Hooks require approval for `rm -rf` / `git clean -fdx` / force-push.
- [ ] Routine writes are unaffected.

**Refs.** List 2 #5,6. Coordinate with BL-1/BL-2 (same MCP files).

## Cross-references and sequencing

- **SEC-1 + SEC-2** both edit `devcontainer.json` and land together as the first PR. (An earlier
  "SEC-1 is a prerequisite of SEC-2" note was a volume-clone artifact: cloning into a volume needed
  working credentials first. With a bind mount the repo is already present, so that ordering no longer
  applies.)
- **SEC-2 <-> SEC-4** are two halves of one design: the mount tiering (`:ro` PDFs, RW vault) and its
  recovery (vault snapshots, PDF immutability).
- **SEC-3 <-> SEC-1**: PAT-scope verification closes the loop on the token.
- **SEC-5 <-> BL-1 / BL-2**: all touch the MCP servers; coordinate so the refactor and verb-gating do
  not collide.
- **SEC-0 / SEC-* <-> BL-5**: Dependabot is the supply-chain lever the security lists reference;
  cross-link, do not duplicate.

**Priority order:** SEC-1 + SEC-2 (first devcontainer PR) -> SEC-3 (server-side, do regardless) ->
SEC-4 (recovery) -> SEC-5 (medium). Backlog (BL-1..5) in parallel.

## Appendix A: ready-to-paste `gh` commands

Run once `gh auth login` has succeeded for `mm-weber`. Create the milestone and labels first (issues
reference them), then the issues.

```bash
REPO=mm-weber/loremaester

gh api "repos/$REPO/milestones" \
  -f title="v0.2" \
  -f state="open" \
  -f description="Hardening and polish: agent blast-radius reduction plus the sourcebooks MCP design review, pyproject migration, and Dependabot."

# --- Labels (--force is idempotent: updates if it already exists) ---
gh label create security          --repo "$REPO" --color B60205 --description "Security hardening / threat-model work" --force
gh label create area:devcontainer --repo "$REPO" --color 0E8A16 --description "Devcontainer / sandbox config" --force
gh label create area:mcp-servers  --repo "$REPO" --color 0E8A16 --description "MCP servers" --force
```
